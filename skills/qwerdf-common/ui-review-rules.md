# UI Review Rules

本文件是 `$pd-ui-review`、`$pd-review` 和 `$pd-fe` 共用的审查适用性、证据、严重性与交接条件。检查项目见 [UI Quality Checklist](ui-quality-checklist.md)，设计约束见 [UI Design System](ui-design-system.md)；入口、模板和专项参考不另定义门禁。

## 1. 审查范围与适用性

- 先明确本轮页面 / frame / 组件、版本、视口、状态和目标。局部审查可给局部结论；不能推及未覆盖页面。用户要求全稿时逐页记录覆盖，未审查部分不得算通过。
- 按对象读取已有产品事实、`ui/ui-design-system.md`、页面规格、组件清单及相关 handoff / frontend-acceptance。截图审查不强制补齐技术设计文件；缺失材料只限制依赖它的判断。
- 产品能力、权限与业务规则来自 PRD / 用户确认；视觉目标来自 `MASTER` 和有理由的 `Page Overrides`。外部参考只贡献适用的设计模式，不能扩大产品范围。
- 默认只审查。用户授权修复后由 `$pd-figma` / `$pd-fe` 处理，事实源问题回 `$pd-blueprint` / `$pd-plan`。本报告不授权提交或部署。

## 2. 证据与三层审查

按要证明的事情选择证据，不把所有证据排成绝对顺序：

| 检查层 | 可证明与限制 |
| --- | --- |
| 视觉扫描 | 当前截图证据证明可见布局；看整页及主 CTA、关键数据、固定栏、用户指出区域的原图 / 局部放大。不能据截图声称已验证键盘、隐藏状态、网络请求或精确 CSS px。 |
| 机器扫描 | 可运行页面检查 DOM / computed style、overflow、可访问性、console / network；Figma 可读节点与变量。只有截图时记“不适用：只有截图”，不因此否定可见布局审查。工具不可用且影响必要断言时记“未验证”。扫描为 0 不能证明视觉通过。 |
| 模板扫描 | 检查本轮同类组件的稳定语义、布局策略与格式。单一对象可记“不适用：无同类组件”。发现问题时沿相关组件族 / 相邻断点追查，写明范围，不无限扩展。 |

- 三层结果如实记录“已检查 / 不适用及理由 / 未验证”。不适用不是缺陷；必要证据缺失不是已通过。不得把未执行步骤填成已执行。
- 自动结构检查不能替代视觉判断，也不能凭词语命中推断无损害或缺陷成立。无法识别的内容、含糊结论和不确定语义交审查者结合原图与产品事实复核；待复核不等于通过，也不等于已确认的 UI 缺陷。
- handoff 自述、修复记录或历史结论不能证明当前视觉已修复；同版本、同状态的截图仍有可见问题时必须记录。版本或状态不同先对齐证据，不任意覆盖其中一方。
- 当前截图证明不了源码 token、实际字体加载或 DOM 行为；这些判断需节点、代码或运行度量。无法区分设计问题与实现偏差时标“归属待确认”。

## 3. 量化阈值与防误报

- 尺寸、断点、状态和组件变体以设计系统、目标平台和产品范围为准。默认值在质量清单维护，不是跨产品硬门槛；合理 Page Overrides 应沿用。
- 基础视觉缺陷包括右侧贴边、字段散落、字体不一致、同类卡片模板不一致、裁切、遮挡、重叠和溢出，按实际用户影响分级。有意省略、局部表格滚动、自适应高度或批准变体不自动算缺陷；检查完整内容是否可获取、操作是否可用。
- 不因紫色、渐变、圆角、单个像素差或主观偏好报错；对照任务、品牌、可读性和设计系统一致性。不能用缩小字号掩盖信息不可读或布局破损。响应式以本次目标平台与实际断点为准。
- 状态适用性按 [质量清单的条件表](ui-quality-checklist.md#4-适用的状态与交互) 判断；蓝图、Figma、技术设计、前端验收与 Code Review 引用同一规则。记录实际覆盖及不适用理由，共享组件状态可引用；未执行的必要检查保持未验证，不借不适用跳过。

## 4. 严重性与不能交付条件

| 级别 | 用户影响与处理 |
| --- | --- |
| P0 | 核心流程不可用，例如提交按钮被遮挡且无替代路径、关键页面白屏或无法完成任务。阻断受影响范围。 |
| P1 | 主流程显著受损或有误操作 / 信息误导风险，例如关键金额被裁切不可恢复、危险操作混淆、必要错误恢复或权限反馈缺失。阻断受影响范围。 |
| P2 | 有证据的局部体验或一致性问题，核心任务仍可完成；记录 owner、验证方式和复查入口，可带残余风险继续。 |
| P3 | 非阻断的文案、轻微间距、对齐或表现优化。 |

不能交付条件：本轮范围存在未解决 P0/P1，或完成必要断言的证据缺失。分别写“有阻断”与“证据不足”，不要把未检查当成产品缺陷。P2/P3 无需清零才能继续，须明确残余风险，不能写“无问题”或宣称相关 finding 已修复。用户明确提出的验收要求仍需满足，不能通过降级绕过。

## 5. Findings 与复查

- 每项 finding 记录级别、页面 / frame / 区域、视口 / 状态、具体问题、用户影响、证据、建议、归属和验证方式。无依据的怀疑列待确认，不升级为 P0/P1。
- 同类问题扫描记录已查组件族、页面、断点与未覆盖范围。用户反复指出的问题优先追查相关范围；未检查范围不得用历史结论补足。
- 修复后在可比较条件下重取证据，再判断该 finding 是否关闭；条件见 [Screenshot Review](../pd-ui-review/references/screenshot-review.md)。不能只凭修复说明关闭，也不把修复一个问题说成全稿通过。
- 结论写明范围、阻断、证据缺口和残余建议。沿用用户格式或旧文档可做等价人工核对，不为凑固定章节重写无关历史内容。

## 6. UI finding 修复交接

- `ui/ui-review-report.md` 保留 finding、视觉证据与复查入口；不要求设计阶段的报告预填工程分类或 slice。用户授权实现修复后，`$pd-fe` 直接引用原报告与 finding ID / 区域，不另复制一份到联调或 Code Review 报告。
- `$pd-fe` 核对现有 UI 设计事实源、当前实现 / 截图证据和 `tech/task-slices.md`：设计要求明确、实现确有偏差且已有 `frontend` / `shared-frontend` slice 覆盖时，记录为 `implementation-defect`，可按同 slice 修复模式重开 `done` slice。分类、映射与修复结果只在前端实现记录维护，原报告保留引用与复查结果。
- 无法映射已有 slice 时，记录 `slice-missing` 回 `$pd-plan`；需要改变页面范围、契约或 UI 设计事实源时，回 `$pd-plan` / `$pd-figma` / `$pd-blueprint`。证据不足或归属不明先补证或人工核对，不猜成实现缺陷，也不新造 slice。
- P0/P1 阻断受影响范围的交付，不阻断用户已授权的该 finding 修复。修复仍检查真实依赖、保持单 slice 边界，按原 finding 路径验证并获取可比证据，再回本报告复查；未复查关闭前不声称该 finding 已解决。
