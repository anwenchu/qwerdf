# Codex Product Delivery 规则

本文件是所有 `$pd-*` skill 的共享规则源。它们是独立的开源 Codex Product Delivery Skills，不绑定任何外部变更生命周期，不参与外部研发流程状态流转。

产品和设计阶段模板见 [artifact-contracts.md](artifact-contracts.md)。工程阶段模板见 [engineering-contracts.md](engineering-contracts.md)。
UI 设计系统和质量规则见 [ui-design-system.md](ui-design-system.md)、[ui-quality-checklist.md](ui-quality-checklist.md)、[ui-patterns.md](ui-patterns.md)、[ui-review-rules.md](ui-review-rules.md)。

## 1. 交付链路

```text
$pd-vet -> $pd-prd -> $pd-blueprint -> $pd-figma -> $pd-ui-review -> $pd-plan -> $pd-fe + $pd-be -> $pd-sync -> $pd-test -> $pd-review -> $pd-git -> $pd-release
```

上述是适用阶段的正式交付顺序；开发期间可先测试或只读审查，不代表跳过正式验收与提交门禁。无关阶段不补造产物。

| 阶段 | 负责 Skill | 默认维护 | 独立产物的条件 |
| --- | --- | --- | --- |
| 想法验证 | `$pd-vet` | `product/idea-brief.md` | 用户、问题、参考、MVP 与验证问题在同一份简报内。已有独立研究材料直接引用。 |
| 需求 | `$pd-prd` | `product/prd.md` | 需求、用户故事、验收、开放问题是章节，不再默认生成四份伴随文件。 |
| UI 蓝图 | `$pd-blueprint` | `ui/ui-design-system.md`、`ui/ui-screens.md` | 仅 UI 范围；流程、导航、页面及组件关系合在页面规格，共用设计系统维护一次。 |
| Figma 交付 | `$pd-figma` | `ui/figma-handoff.md` | 复用设计系统；确需候选比较时才维护 `ui/ui-directions.md`，保留真实写入与视觉证据。 |
| UI 审查 | `$pd-ui-review` | `ui/ui-review-report.md` | 只维护实际范围的 finding、证据与复查结果。 |
| 技术设计 | `$pd-plan` | `tech/tech-plan.md`、`tech/task-slices.md` | 两端设计、数据、真实输入、接线映射、实施顺序和风险是方案章节；跨端 / 外部共同消费的契约、实际 SQL 执行清单才单独维护。 |
| 前端开发 | `$pd-fe` | 原位更新 `tech/task-slices.md` | 状态、简短结果、UI 检查及证据引用写回本端任务，不默认生成实现日志、文件清单、开发备注、验收副本。 |
| 后端开发 | `$pd-be` | 原位更新 `tech/task-slices.md` | 同上；必要 SQL 记录回已有执行计划，不重复抄写。 |
| 联调 | `$pd-sync` | `sync/integration-report.md` | 计划、场景、差异与修复路由放同一报告；需要修订时直接回原方案 / 契约，不另建修订副本。 |
| 测试 | `$pd-test` | `test/test-report.md` | 计划、用例、结果、回归和未覆盖范围在同一报告。 |
| 代码审查 | `$pd-review` | `test/code-review.md` | 正式审查保留 findings；只读检查且未要求写文件时直接回复。 |
| Git | `$pd-git` | 回复中的范围、检查结果、commit / PR 文案 | 用户指定落文件或平台实际需要时才写说明文件；提交权限与门禁不变。 |
| 上线准备 | `$pd-release` | `release/release-notes.md` | 计划、检查、回滚合在本文件；独立运维消费者确需计划 / 回滚清单时才拆出唯一对应材料。 |

每个独立任务默认围绕 `product/prd.md → tech/tech-plan.md → tech/task-slices.md` 三份主文档推进，按实际阶段和变更范围维护，已确认的共用内容直接引用。并非每项需求都要走完所有阶段；UI、契约、SQL 和正式验证证据按实际适用性维护。上述是默认产物与职责的唯一清单，不把模板目录当生成清单。

章节内容多不等于必须拆文件。只有确有独立消费者、执行 / 审核用途，或去重后仍无法定向审阅的稳定主题才单独成文，并从主文档引用唯一事实源。已有分文件沿用已核实来源，未授权不迁移、合并或删除，不再把它们全量复制回主文档。详见 [生命周期规则](artifact-lifecycle.md)。

## 2. 默认工作目录

先确定当前独立任务的输出根目录，以下阶段相对路径均以该目录为基准。小型、有边界的需求可直接使用 `pd-work/<name>/`，只创建当前阶段实际需要的文件及目录：

```text
pd-work/<name>/
  product/prd.md
  tech/tech-plan.md
  tech/task-slices.md
```

UI、独立契约、SQL、正式报告按上方阶段表的适用条件维护，不提前建齐目录。

超大需求包含多个独立交付单元，或用户明确要求独立任务 / 独立返工时，在项目目录下用 `tasks/<稳定任务名>/` 分开维护。沿用已有等价目录约定。项目只保留简短索引和实际共用事实，详情、实现切片、状态及证据归各任务：

```text
pd-work/<project>/
  README.md                          # 项目导航，复用已有总览也可
  TODO.md                            # 从任务来源生成的未完成视图
  product/prd.md                     # 需要时维护共用需求与验收
  tasks/<task-name>/
    product/prd.md                   # 仅本任务新增或修订的需求与验收
    tech/tech-plan.md                # 本任务设计，引用共用契约
    tech/task-slices.md              # 本任务前后端顺序、状态与续作
```

- 用户指定当前任务目录时直接沿用；否则先从用户指定任务、项目索引或当前续作定位所属目录。独立任务已选定后，各阶段都使用该根目录，校验命令的 `--root` 同样指向它。推进单项但只有项目信息且存在多个候选时，按已有明确顺序或任务关联定位，仍无法确定才问必要选择，不按文件修改时间猜任务。
- 用户要求项目整体设计、审查或进度汇总时，以项目索引界定范围，按需核对相关任务，变更和状态分别回所属任务维护，项目共用事实在原处更新。整体覆盖与跨任务验收仍按原范围检查。
- 项目索引只记稳定任务名、范围 / 交付结果、验收引用和目录链接，不手工再维护一份子任务状态或完成百分比。查进度时定向读取相关任务清单，按任务分别汇报；子任务同名 ID 须带任务路径定位。项目级集成 / 共用工程任务有自身范围和证据，不用来复制子任务的当前进度。
- 同一交付动作下的前后端实现切片、一般缺陷修正或普通审查意见仍在所属任务原位维护。明确独立的返工 / 新交付单元单独建任务目录，写明原任务引用、新范围、验收和受影响结论。每个切片不自动创建子目录，也不递归复制全套阶段文档。组织拆分不改变原业务范围或整体交接要求。
- 共用需求、设计系统、契约和跨任务约束只维护一处，任务记录来源及适用版本 / 段落和差异。共用事实变化时定向检查受影响任务，修订相关设计 / 验收并重开受影响条目，保留旧证据和修订依据。必要契约或安全缺口仍限制真正消费者，其他输入齐备的独立任务继续。

上述是目录示意，按本任务当前阶段创建实际需要的材料。仅修实现而需求 / 契约未变时引用原事实源，无需补一套空 PRD / 方案。项目索引复用已有总览；确需新建时只建一份，不为每个子任务再建 README。

阶段文件名在当前任务根目录内保持 canonical path。读取上游材料时沿任务中的有效引用读取共用或既有来源，已有平铺文件可作 legacy fallback。新材料写入已确定的任务目录，既有未变事实保持引用。既有集中目录、任务清单或工具只有在获准整理并核实消费者后才迁移，迁移保留稳定 ID / 归属映射、状态与证据，任何条目始终只有一份可写状态源。仅优化 skill 时保留现有项目产物。

### 项目待办视图

- 多任务项目复用一份派生 TODO，所属任务清单是唯一可写状态源。完成项只移出视图，原记录与证据保留，重开后重新出现。已有手工文件或归属不明的文件先保留，不自动接管。
- 已确认但尚未拆解 / 归属的事项在原项目索引留简短来源引用；落实到任务并核对覆盖后移除导航行，保留原确认依据。未通过的必要验证和未闭合父项保持可追踪，不凭编码 done 清空待办，也不把条目占比当业务完成率。
- 维护多任务项目视图时才读取 [待办工具用法与输入格式](engineering-contracts.md#待办工具用法)。更新源后，在任务变化、交接及项目进度查询时刷新；只读请求只核对并按源汇报。无关单任务和普通命令不反复刷新。
- 汇总缺口或刷新失败必须显式报告，不把旧视图当当前结果；源更新不回滚，继续不依赖视图的独立工作。视图不解除真实输入、安全、验收及提交约束，不证明需求完整覆盖或可上线。

## 3. Skill 执行规范

- 读取或写入阶段材料前先按目录规则确定当前独立任务根目录，摘要给出该路径及共用来源。目录内相对路径、任务 ID、状态和验证结论均属于本任务；跨任务引用带目录定位。
- 每个 `$pd-*` skill 只读取本阶段需要的公共模板和上游产物，避免一次性加载无关模板。
- 开始工作及恢复上下文时先按 [产物生命周期规则](artifact-lifecycle.md) 确定当前入口、相关产物；展开需求 / 方案正文前先做规模评估，过大先拆交付单元；当前文档原位更新、证据留必要增量，禁止以反复生成整套快照代替维护。
- 触发描述必须说明 “做什么” 和 “什么时候使用”，不要只罗列命令名。
- 产物必须可复用：写清输入来源、关键判断、未验证假设、验证证据和下一步。
- 缺少关键输入时先核对已有资料与决定；仍缺且须用户提供或决策时，列出具体缺口定向提问，不生成看似完整但依据不足的文件。工程漏项按 [共享分类规则](technical-design-rules.md#工程漏项与业务决策分类) 处理，不把每个缺字段都变成业务选择。
- 需要修改代码、设计、Git 或外部系统时，遵守对应 skill 的边界；没有明确授权时只做计划、报告或文案。
- 检查围绕本轮交付结果安排，阶段模板和清单定义覆盖范围，不要求每次编辑都执行一遍。相关问题集中修正后检查受影响范围；输入、产物与覆盖仍有效的证据可引用，不因换阶段、恢复上下文或更新报告而自动重跑。必要验收与安全检查仍须满足；已满足要求后的可选润色不继续挤占当前交付。执行结果在原任务 / 报告合并记录方式、结果和必要证据，不逐命令生成日志。
- 当任务反复出现相同机械步骤时，优先把步骤沉淀为脚本或公共模板，而不是在多个 skill 中复制长指令。
- 修改 skill 描述、触发词或阶段边界后，检查 `evals/cases/trigger-queries.json`，确保 should-trigger 和 should-not-trigger 样例仍然成立。

### 产品事实与参考使用 Gate

- 产品事实源优先级：用户明确说明、PRD、需求清单、产品设计输入、UI 页面蓝图、现有代码 / 数据结构高于竞品、截图、Figma 参考和视觉样例。参考材料不能覆盖或扩展产品事实源。
- 设计前必须先建立产品事实锁：产品名称、目标用户、核心场景、支持的业务对象、页面 / 导航范围、明确不做的内容。
- 外部参考必须拆成两类：可借鉴的抽象视觉 / 交互模式，以及不得带入的业务语义 / 导航文案 / 产品模块 / 交易品类 / 品牌资产 / 受保护文案。
- 参考对象中出现但产品事实源未出现的功能、页面、tab、资产类型、合约类型、营销入口、社区 / 活动 / copy trading 等模块，默认视为参考禁区，只能写进“不得带入 / 不应照搬”，不能成为产品范围、页面结构、Figma frame、API 契约或任务切片。
- 如果无法判断某个参考元素是视觉风格还是产品能力，先提问；无人确认时按不带入处理。
- 设计输出必须能追溯：页面、组件、状态、导航和关键文案都要来自产品事实源或明确的用户确认；参考材料只贡献风格、布局密度、信息组织方式或微交互。
- Figma / 截图是表现层参考，不是需求来源。Figma handoff 与 PRD、product-brief 或 UI 蓝图冲突时，先记录冲突并停止，不把冲突内容下推到技术设计或实现。

### UI 设计系统与质量 Gate

- `ui/ui-design-system.md` 是 UI 设计系统事实源，`MASTER` 定义全局规则，`Page Overrides` 只记录必要页面差异。不得在页面规格、Figma handoff 或前端技术设计中复制出互相冲突的局部设计系统。
- `$pd-blueprint` 必须在产品设计输入阶段明确产品类型、用户角色、核心任务、信息密度、视觉气质、页面模式、导航结构、关键状态和设计风险，并生成设计系统草案。
- `$pd-figma` 在生成 UI 方向或写入 Figma 前必须读取或补齐 `ui/ui-design-system.md`；UI 方向只能改变呈现方式，不能改变产品范围。
- 候选先在 Figma 展示、用户选择后深化；已有方向或仅本地预览的处理统一见 [pd-figma 的方向交付流程](../pd-figma/SKILL.md#gate-1在-figma-比较并选择-ui-方向)。候选不等于正式 handoff，不据此进入技术设计。
- `$pd-figma` 创建或修改 Figma frame 后必须执行交付前截图级视觉 QA：每个目标 frame / 断点都要有截图证据，检查遮挡、重叠、溢出、字体、间距、安全区、状态和产品类型适配，并记录同类问题扫描。
- `$pd-figma` 不得只凭文字或图层描述声称已修复；用户指出的字体、间距、遮挡、重叠、突兀、不整齐或移动端溢出问题，必须修复后重新截图并检查相似 frame / 组件 / 断点。
- `$pd-ui-review` 是独立 UI 设计质量审查 gate，默认放在 `$pd-figma` 后、`$pd-plan` 前；也可在 `$pd-fe` 后用于视觉回归。它只输出 `ui/ui-review-report.md`，不改设计稿、不改代码、不提交。
- `$pd-ui-review` 必须审查产品事实源、`ui/ui-design-system.md` 的 `MASTER` / `Page Overrides`、Figma handoff、Figma frame、截图或本地页面 URL；发现 P0/P1 时必须把归属指向 `$pd-figma`、`$pd-fe`、`$pd-plan` 或 `$pd-blueprint`，不得泛泛评价“美观”。
- `$pd-ui-review` 的阻断、残余风险及授权后的修复交接统一遵循 [UI Review Rules](ui-review-rules.md)，不以交付阻断禁止修复原 finding。
- UI 审查适用性、严重性和交接条件统一见 [UI Review Rules](ui-review-rules.md)；检查项与默认尺寸见 [UI Quality Checklist](ui-quality-checklist.md)。截图不要求运行环境证据，不适用状态不强制生成，未覆盖范围不得宣称已验证。
- `$pd-plan` 必须把 `ui/ui-design-system.md` 和 `ui/figma-handoff.md` 转成前端技术约束：组件复用、状态覆盖、响应式、可访问性、表单校验、错误映射、空态和 UI 验收方式。
- `$pd-fe` 必须读取 `ui/ui-design-system.md` 和 UI 质量清单后实现；完成后在本端任务的验证记录中（已有独立验收源则引用）记录本次平台、无横向溢出、文本不重叠及适用状态的检查证据；状态适用性统一遵循 [UI Quality Checklist](ui-quality-checklist.md#4-适用的状态与交互)，不适用写明理由。
- `$pd-review` 涉及 UI diff 时必须执行 UI Review：检查设计系统一致性、产品类型匹配、信息层级、响应式、可访问性、状态覆盖、表单 / 表格 / 图表质量，并按 P0/P1/P2/P3 输出带证据的 finding。
- SaaS / CRM / 管理后台 / 操作台类产品默认采用克制、密集、可扫描、效率优先的界面方向；不要把 landing page hero、过度卡片化、装饰性插画或大面积氛围图带入操作型产品，除非 PRD 明确要求营销页面。

### UI 职责边界

- `$pd-blueprint`：定义产品事实、页面范围、产品类型、信息密度、页面模式、关键状态和设计风险，生成 `ui/ui-design-system.md` 草案；不写 Figma 高保真。
- `$pd-figma`：确认 / 补齐 `MASTER`，生成 UI 方向，写入或整理 Figma，完成截图级视觉 QA 和 `ui/figma-handoff.md`；不改 PRD、技术方案或代码。
- `$pd-ui-review`：独立审查 Figma frame、handoff、截图和本地页面 UI 表现，输出 `ui/ui-review-report.md`；默认只审查，不改设计稿、不改代码、不提交。
- `$pd-plan`：把设计系统、handoff 和 UI Review 结论转成前端技术约束和 task slice；不擅自新增页面、导航或视觉风格。
- `$pd-fe`：按设计系统和技术设计实现，并在本端任务的验证记录中（已有独立验收事实源则引用）记录桌面 / 移动端截图、状态、无横向溢出和无文本重叠证据；不修改上游设计事实源来掩盖实现偏差。
- `$pd-review`：做代码级和交付级审查，读取 `ui/ui-review-report.md` 和前端验收证据；发现 UI P0/P1 时阻断 `$pd-git`。

### Figma 连接与会话复用

- 调用前读取当前工具 schema，按其要求显式传入 link_id 等连接参数；参数缺失 / 校验失败应补齐原调用，不是授权失效，也不是要求用户选择账号的依据。仅有一个可用连接时直接采用其枚举值；用户已明确选定、或已确认删除多余连接时，不因旧工具说明仍列出多个同名项而重新询问。
- 当前聊天缺少连接映射时，先按项目恢复入口，在 read_thread 可用的环境读取同一项目、同一 fileKey 的成功文件调用；没有指定入口时，可用 list_threads 定位相关设计交付聊天后定向读取。读取时包含工具参数（支持时设 includeOutputs=true），首批未命中则沿返回的 cursor 定向翻页；只有工具状态成功且响应未报错的文件调用可作映射，whoami / create_session 成功不能替代文件访问证据。将 arguments.link_id 与当前可用连接核对，唯一匹配即复用；不能只凭聊天标题、摘要、同名账号或排列顺序选取。工具不可用时使用当前合法工具记录 / 项目提供的恢复入口，不扫描认证存储。读取记录不等于向另一个聊天发送消息。跨独立任务只恢复连接选择，不复制旧 sessionId；按提供方要求建立本任务会话。用户当前明确选择优先于历史；记录仍有冲突或已选连接不再可用时才澄清必要选择，不遍历认证。
- 连接一经用户选定或在当前任务中成功使用，后续调用固定使用该连接；工具发现列出其他同名连接不是切换理由。已有成功文件访问时直接继续所需操作，不先调用 whoami 做健康检查；不并行探测其他连接。此约束同样适用于 UI 审查和上下文恢复。
- 工具明确返回“Authentication … requested and accepted. Retry this tool call now.”时，表示本次授权流程已完成，不再向用户提出重连：按提供方允许的安全重试方式，在同一连接重试原调用一次。写入结果可能已生效时先只读核实，不盲目重放；同样提示再次出现则停止该路径，报告具体错误，不换账号或循环认证。

- 实际访问 Figma 前，先从用户当前要求、会话中已明确的选择和已有成功调用确定连接 / 账号及目标，不为“确认一下”遍历所有 Figma 连接、并行调用多个 whoami 或试探可能触发授权的工具。加载相应 Figma 技能只是读取操作规则，不代表要重新连接账号；已有选择沿用，同名连接不当作同一账号，也不凭排列顺序猜用户选择。确实无法唯一定位时只澄清必要的连接选择，不用逐个认证来探测。
- 沿用选定连接的有效会话，参数和工具能力以当前提供方说明为准。有 create_session 且本任务尚无可用 sessionId 时，按工具要求在取得 fileKey 后、首次文件读写前建立会话（新建文件按该工具要求先创建文件），成功取得可用 sessionId 后在接受它的调用中原样复用。“创建一次”指建立后复用，不是只允许一次调用；发起过调用不等于已经取得有效会话。跟进修改、检查、完成同一工作，或该工作切换文件，都不单独构成新建会话理由；真正独立的新任务按提供方要求建新会话。用户明确切换账号时不把旧账号 session 带到新连接；也不将已确认账号误当作已存在有效文件会话。
- 首次建会话失败 / 超时未取得可用 sessionId，或工具明确报告 session 失效时，先复用当前合法工具上下文中可恢复的有效会话；确实没有且账号授权有效，可按提供方允许的方式在同一连接恢复 / 补建一次。该恢复仍失败则停止该路径；没有新证据或用户处理，不继续重建。认证失败先走下方重连流程，不能绕过必要会话前置直接读写文件，也不能因建会话失败而重新创建已经建好的文件 / 页面。
- 临时只读失败可以在同一连接 / 同一有效会话中做一次有理由的重试；同一故障持续则停止该路径并记录具体未读到的文件 / 节点、错误和影响，不反复 create_session、whoami 或改走另一账号授权。
- 明确返回认证失效 / 需要授权时不自动循环重试；如果任务确需继续访问，说明是哪个已选连接失效及影响，提出一次必要的重连请求，等待用户处理。用户完成重新授权后，依据工具返回的账号 / 连接上下文恢复：同一账号的会话仍有效则复用，没有可用 sessionId 或明确失效则按上方规则恢复 / 建立，不因先前调用失败拒绝必要建会话；账号变更时不复用旧账号 session。恢复失败仍停止，没有新增证据或用户动作不循环重连。文件权限不足、目标不存在、连接不可用和认证失效分别报告，不能一律要求重登；也不能假称已有授权永久有效，不自动切换账号、断开连接或修改全局连接配置。
- 写入恢复遵循提供方的安全重试标记；只有明确可安全重试的失败才按该规则修正后重试。超时或可能部分生效且结果不明时，先沿原选定连接和合法会话只读核实本轮变更；必要的授权 / 会话恢复可先完成，但恢复成功不证明原写入未生效。核实已存在的文件 / 页面 / 节点后复用，只补已确认缺失的部分；无法核实的部分保留“写入结果未知”，不重复创建、不按同名就认定为本轮结果，也不删除重做。
- 交付记录按方向 / 页面保留实际写入状态和证据：未写入表示尚未发起；失败表示已确认未生效；部分写入表示已确认仅部分生效；已写入表示本轮写入已确认，视觉 QA 另记。无法确认是否生效的项必须标为“写入结果未知”，列出已知成功部分、待核实目标和恢复入口，不强行归为失败 / 未写入 / 全部成功。候选与正式交付模板、输出摘要沿用此定义；存在未知项时不能宣称受影响范围已完整交付，其他独立且证据充分的部分可据实交付。
- 已有 handoff、截图或本地材料足够完成本轮判断时，不额外触发账号核查。Figma 不可读则保留必要的设计证据缺口，仅继续不依赖缺失证据且原交接 / 依赖 gate 已满足的工作；不能把旧截图、连接成功或 session 创建成功说成最新设计读取 / 视觉验收通过，必要原稿缺失时不凭猜测实现对应设计。
- 连接与 session 复用信息只使用当前任务中工具已提供的合法上下文，不能编造 sessionId 或将另一个账号的会话当作当前会话。报告仅保留定位问题所需的非敏感证据，不把账号邮箱、实际连接标识、sessionId、token / cookie 写进公共 skill、仓库示例或持久配置来实现“记住登录”。

## 4. 安全与意外最小化

- Skill 内容不能包含与描述不符的隐藏行为、越权访问、数据外传、恶意脚本或误导性流程。
- 不把 token、cookie、密钥、敏感信息写入命令、日志、产物或 PR 描述。
- 涉及 Git、Figma、发布平台、外部 API、真实部署或写入外部系统时，先说明目标、范围和动作后再执行。
- 默认不执行 destructive、push、deploy、publish、sync-to-external 等高影响动作，除非用户明确要求并且对应 skill 允许。
- 读取外部或远程规则时记录来源；规则版本可能变化时，不把旧规则当作当前事实。

## 5. 规则来源

外部来源与借鉴方式见 [References](../../docs/references.md)，运行当前阶段无需加载来源历史。

## 7. 设计与工程 Gate

### 适用范围与产物

- 先根据本轮确认范围判断 UI、前端、后端、跨端联调及 SQL 是否适用，在 `tech/tech-plan.md` 记录依据。阶段产物表是适用时的目录，不是每次全量生成清单；不涉及的端或 UI 不要求补造设计系统、Figma 或空任务。不得以“不适用”掩盖实际受影响的页面、调用、数据变更或必要验证。
- `tech/tech-plan.md` 的“真实输入与验证准备”记录实际使用的工具链、外部依赖及编码 / 验证用途；已有独立 readiness 事实源则引用它；不要求无关的 JDK、Node、数据库或 HTTP 服务。SQL / migration 涉及时维护 `tech/backend/sql-execution-plan.md` 的文件、顺序、环境、验证、回滚与风险；不涉及时在技术方案说明依据，已有执行计划须同步为“不涉及”，不为无 SQL 的范围新建空清单。
- 涉及 UI 时沿用 UI 设计系统与质量 Gate、必要 handoff 及独立 UI finding；UI Review 未执行或截图缺失须记证据缺口，不假称验收。无 UI 的范围不因缺 Figma 而阻断。真实接入允许项目已有相对路径 / 同源路由，不强加绝对 base URL。

### 开发交接与依赖

- 技术依据、范围分类和交接完成统一按 [技术设计规则](technical-design-rules.md) 判断。`$pd-plan` 未达到本轮交接条件不进入开发；只要求检查时不启动实现。文件齐全或任务标 done 不替代契约可落地依据。
- 设计前确认修改仓库、开发分支及修改二方包的开发版本；前后端实施均核对同一份记录，执行 [仓库、分支与二方包版本规则](technical-design-rules.md#仓库分支与二方包版本)，不在各端另定口径。
- 前后端使用同一份已确认契约与方案中的接线映射；任务来源、状态与各端顺序按下方任务清单规则读取。契约可落地且本轮设计交接结论成立才进入实现；不以独立契约任务的状态替代交接核查，实现者不单方面修改共享契约。
- 开工前读取目标仓库约定、适用编码规范与相关实现。每片标记完成前，检查实际 diff 和受影响的调用路径是否符合规范与契约，修正本片引入的明确违规并复查受影响部分。检查结果写回原任务证据，轻微风格建议按原审查规则处理。
- 真实依赖 Gate 按当前动作判断：编码必需输入只有 `ready` / `not-required` 可执行，`unknown` / `blocked` / `mock-only` 停止受影响动作。只影响验证的限制按业务推进规则记录，不扩为全局停工，也不降低原完成标准。
- 本地真实服务、官方本地容器或测试环境真实服务可提供 ready 证据。技术实现与测试通过证据禁止 mock client / server、stub adapter、fake repository / downstream、fixture-only 数据流、测试替身或 contract simulator；不能接入真实必需依赖时记录具体阻断，不用替身冒充。
- 任务按本端顺序推进；同一业务动作内输入齐备的相关改动可集中实现和验证，完成结论仍逐项核对，只更新自己负责的权威条目。前后端并行、共享产物准备、blocked 恢复及停止条件按下方相应规则执行，不因对端未完成而等待，不绕过真正的输入缺口。
- 合法实现缺陷可按下方联调与验收交接规则重开已有 slice；UI finding 沿用 [修复交接](ui-review-rules.md#6-ui-finding-修复交接)。范围或契约改变回 `$pd-plan`，不扩成未授权改造。

### 验证与审查

#### 验证循环与退出

- **先定业务收尾与整个循环的限额**：在当前任务续作或本阶段已有产物中，简短写明本次要满足的交付结果 / 验收缺口、收尾信号、最小检查，以及适合当前风险的截止时间或纠错轮次上限。围绕同一验收缺口的一次有目的尝试算一轮，可包含诊断、相关修复及最小验证，不以修改代码为前提；只读排查或验证也计入，失败、超时或中断不返还额度。一次已约定尝试内的准备、相关操作和查看结果不按工具调用数机械拆轮，但根据结果改变诊断方向、再次验证须计新轮，不能无限并入旧轮。限额覆盖整个修改、搜索、编译、测试、截图与排障循环，不只覆盖单条命令。沿用已有可用限额，恢复上下文保留剩余量；换文件、冒出局部细节、改任务名或出现新假设都不自动重置。没有可信计时就用有界轮次，不编造耗时，不另建计时台账。单项稳定检查用其现有超时 / 失败退出条件即可，不强制拆出多轮计划。
- **再改或再跑须有可核实的目的**：下一轮须说明当前验收仍缺什么、上轮证据支持哪个修改、什么结果会收尾。相关新证据只说明值得在剩余限额内继续，不等于业务已推进，也不自动续期；到界后的必要收尾仅按下一条复核，不扩成新一轮探索。局部 diff、新细节或检查通过不能替代本轮可观察的交付结果。当前必要检查已满足就收尾，非当前验收或已证实风险所需的加固记回原任务或本阶段产物后置，不继续为假设风险打磨。同一失败没有相关输入变化或可检验的新依据时停止原尝试。事先约定的有界采样作为一次整体尝试计数，内部仍按原次数上限和截止时间执行，保留所有结果，不重置外层限额，也不替代必要回归。
- **到界先复核收尾，否则退出原循环**：达到本次截止时间、轮次上限或预先约定的停止条件，先判断是尚未收敛的探索，还是已有证据明确定位、可在授权内完成的当前必要修复。后者可在原记录简记最小修复范围、通过信号及有界退出条件，完成一次必要收尾及相应验证，无须为此换技术路径或重做设计；已经启动且正常推进的必要回归，可在原命令超时和退出条件内完成，不因业务窗口刚耗尽就中断。收尾不是重新发放整轮额度，不能延长原命令超时、增加探索 / 采样，或把新问题接成下一轮收尾；收尾失败、出现新未知或达到所定退出条件后，按原资源退出规则分流。必要安全修复可收尾，但“安全”标签本身不构成无限续期的依据。
- **未收敛尝试的分流与恢复**：不满足上述收尾条件时停止原尝试，在原任务或本阶段产物记录未完成环节、证据和恢复条件，先续接当前仍可推进的交付环节，再转其他输入齐备的独立工作；确无获准动作才据实交接。限额耗尽不是外部阻断、放行或停止全部授权工作的依据。适用的安全条件或原验收未通过的范围仍不标 done / 已交付，不让消费者使用未就绪产物。重入耗尽路径须有已生效输入变化、已完成设计修订，或由前次证据支持、直接针对原验收缺口的不同修复路径及有界判别检查；在原记录保留已耗尽尝试及新的有限范围，不覆盖旧限额。仅换理由、局部假设、延长时间或重新编号不构成恢复依据。
- **长检查超时与资源退出**：按项目配置、既有耗时和检查性质设置合理的命令超时及可执行退出方式；工具返回会话 ID 或一次等待结束不等于执行超时。失败或超时后安全停止本次自有检查，保留证据，区分失败、超时未完成与结果未知；确认进程 / 子进程结束及共享资源可用。仍占用或状态不明时，只暂停依赖该资源 / 结果的动作，其他独立工作继续；恢复前核实资源与必要结果。无法安全限定执行时改选有界检查，保留原验证缺口。

#### 工程验证覆盖与证据

- **检查覆盖任务，不按每次编辑重复构建**：涉及接口、状态或数据结构调整时，先按原设计定向核对本轮入口、直接调用方、装配、数据映射及相关测试，在原任务记录一份简短的待接通清单；已有清单原位补差异，不全仓重查、不为每个字段拆新任务，局部修改可只记受影响项。旧测试也是消费者，生产改动与测试迁移同批处理；不恢复已作废设计来迎合旧测试，也不删掉仍适用的断言。失败先区分真实行为回归、旧测试未迁移和验证入口问题；有同根因证据的调用 / fixture 漏项集中补齐，不只修每次报错的一个字段再编译，无法确认同因的不盲改断言。发现新直接消费者时补回原清单，不重启整套分析。在授权、本端顺序和实际输入允许时，按清单集中完成同一业务动作内可控阶段的相关改动，再执行覆盖该阶段的检查集合；同一次编译、测试或 UI 检查可覆盖多个条目，逐项核对原要求并引用对应证据，不为每个字段 / helper / 小补丁各跑一遍全套检查、刷新总表和写摘要。需要提前排除具体风险时允许定向检查，不能只因改了代码就重跑；危险操作、向消费者交付前的必要安全检查及原定回归仍须执行，未验证的实际产物不能作为后续任务的 ready 输入。检查覆盖每项要求后才逐项标 done，不合并成一个永远无法验收的大任务。
- **验证入口与当前产物对应**：优先使用项目已有构建 / 测试入口；按检查类型核对实际工作目录及适用的输入、输出和覆盖范围，临时脚本、隔离构建与增量缓存同样适用。纯编译、类型 / 静态检查核实当前源码、适用配置 / 依赖与结果即可，不强制执行测试断言；执行测试时，再核对所消费的编译产物、测试选择范围和实际执行数，确认预期断言实际执行。构建通过不能写成测试通过，必要测试仍按原验收执行；选择器未匹配用例、测试全跳过或只编译测试源码，不能作为该测试范围通过的证据。可复用构建工具可信的增量记录，不要求每次全仓 clean 或另建校验台账；删除 / 改名、依赖或 classpath 变化时失效并重建受影响输出。旧成功标记、旧报告、复用目录存在或一次局部编译成功，不能证明整批当前源码已编译 / 测试通过。入口的目录 / classpath / 选择器错误先作为验证入口问题集中修正，不据此改业务语义或削弱断言；无法确认对应关系时保留未验证范围，按原限额处理，不靠反复打补丁维持另一套构建系统。共享检查的覆盖映射写回已有任务 / 报告，后续阶段核对证据有效性后引用，仅对变化影响或原未覆盖的必要要求补验；正式真实链路、安全及验收门禁不因引用证据而省略。
- **保留必需验证并继续可做的工作**：权限、幂等、事务、资金安全和约定验收仍按原要求实施和验证。验证遇到卡点时，在原任务或当前验证报告记录受影响的验收、已有证据、缺口和恢复条件，随后继续获准且输入齐备的独立实现或验证。必要验证尚未通过的范围保留原完成限制；SQL 或协议包操作受限时，按下方业务推进规则继续具备输入的真实接线。
- 允许在开发期间执行输入齐备且获准的测试及只读 Code Review，不要求等待全部联调完成；缺少上游报告或环境只限制依赖它的验证和总体通过结论。单项通过、静态检查通过或“未发现问题”不等于联调 / 整体测试通过或可提交。
- `$pd-sync` 正式联调遵循下方联调与验收交接规则：相关实现完成、实际必需依赖就绪、生产路径无模拟替代。报告须记录真实依赖验证、Mock 禁用检查、范围和证据；无跨端交互的静态内容可注明联调不适用及依据，不能把应动态获取的数据写死后称为静态页。
- 联调修复路由：契约不清 / 冲突为 `contract-mismatch` 回 `$pd-plan`；契约明确但实现不符为 `implementation-defect` 回归属端；确认的权威任务源无覆盖为 `slice-missing` 回 `$pd-plan`（先排除视图滞后）；任务归属 / 顺序不可执行为 `slice-model-invalid` 回 `$pd-plan`；环境问题为 `environment-blocked`。联调只记录不改代码；只在契约 / 任务需修订时更新差异和修订文档。
- `$pd-test` 按用例实际依赖执行可运行测试；报告分别列单项结果、未执行项和整体结论。适用联调未通过 / 未确认不适用、真实依赖未验证或必要 SQL 未执行时，不能报告整体通过。无外部依赖的代码可执行真实单元测试，不要求引入数据库或远程服务。
- `$pd-review` 可提前输出带证据的 findings，缺少联调 / 测试证据不阻止继续读代码；仍须记录未覆盖范围，不能输出“可提交”。P0/P1、失败测试、契约差异及必要证据缺口分别回相应修复阶段。

### 正式提交与上线

- Commit readiness gate 是正式提交的共同条件：相关实现完成；`sync/integration-report.md` 明确通过或有依据的不适用；`test/test-report.md` 明确通过且无未解释高风险缺口；`test/code-review.md` 无未解决 P0/P1 并覆盖当前改动；提交范围无未解决漏提 / 多提风险。不得以提前测试 / 审查或任务 done 代替这些条件。
- `$pd-git` 可先整理文案及缺口，未满足共同条件不得执行提交。实际 add / commit / push 权限及文件范围按 Git 与发布边界执行，不因门禁通过自动获权。
- `$pd-release` 可编制草案；正式上线结论须核对联调、测试、审查和适用 SQL 证据。SQL 未验证、生产顺序 / 必需备份 / 回滚不明确时不得称可上线；生成命令不代表执行授权。

## 8. Task Slice 规则

任务按前端、后端分别列出顺序，状态使用 `pending`、`in_progress`、`done`、`blocked`。必要工程准备排入实际负责端的清单；契约完成在技术设计交接中确认，联调 / 测试按验收范围衔接。不另设任务类型枚举、并行标记或双向依赖列。

### 任务清单与开发顺序

- 每个独立任务默认只维护自己根目录内的 `tech/task-slices.md`，`$pd-plan` 必须实际交付本任务清单，不只在聊天列步骤。项目总览只链接各任务的权威源，各任务清单只维护本任务条目；不生成 `task-slices.json`、同内容的另一格式或同步脚本。AI 能读取 Markdown，不以“便于 AI / 自动化”作为增加 JSON 的理由。
- 只有已有且本轮仍实际使用的工具确实需要 JSON 时，才沿用兼容例外。先定位真实读写代码 / 配置、执行入口及用途，在 Markdown 的来源说明中引用依据并确定唯一权威源；仅有旧 JSON 文件、历史约定或为重复维护两份清单而写的转换脚本，都不足以证明必要性。不得为制造例外新建工具、渲染器或 JSON schema；未核实消费关系时不新增或重建 JSON。
- 已确认 JSON 是现有工具的权威输入时，只更新 JSON，Markdown 只从该源派生显示，优先复用已有生成方式，不要求另建渲染器；若 JSON 只是必要工具的导出格式，则仍只维护 Markdown，JSON 按需单向导出。各阶段的 ID、归属、顺序、状态、完成标准与证据都从同一权威源读取，不双向手改；不为该例外另造同步系统或强制迁移现有工具。
- 旧 JSON 没有实际消费者时，在获准整理来源时核对来源及有效进展，将当前任务统一到 Markdown；旧文件不再作为当前状态来源，不自动删除或重写历史。既有来源 / 状态不明时先查原记录和实际消费者，只暂停受影响的调度 / 完成判断，不能凭默认格式覆盖未核实进展。
- 更新前重读权威源，仅修改自己负责的条目，保留其他执行者更新与证据。默认 Markdown 直接更新原文件；项目 TODO 按上方共享视图规则刷新，其他格式仅按已证实兼容例外派生。来源明确而视图滞后时只从源刷新；权威更新已成功但派生刷新失败时保留成功更新、注明滞后，不回滚或用旧视图汇报。真正依赖该视图的消费先修复或明确改读权威源，其他独立工作继续；不按修改时间、较乐观状态或文件格式猜谁正确，不整表重置。
- 任务清单覆盖本轮确认的前端、后端、必要准备与联调 / 测试。实现 slice 围绕一个可独立核验的业务动作或能力增量：写清输入 / 契约引用、实现归属、可观察结果、必要异常 / 安全边界及验证证据，可引用技术设计而不重复全文。不要将多个独立业务结果合成长期无法验收的大项，也不按每个类 / helper 机械拆碎；必要工程准备可以单独成项，但要说明真实产物、消费者及完成信号。不用固定工时、文件数或任务数量限制粒度。某端不涉及写明依据，不补造空任务；任务无覆盖的确认需求属于漏项。
- 前后端各自按业务实施顺序列任务，顺序与状态都来自同一权威源；JSON 权威源沿用其已约定的数组顺序或排序字段，Markdown 只展示，不另编一套顺序。先安排必要准备与当前可验收的业务结果，不以全部最高优先级代替顺序。每端从首个未完成项核查并推进；遇到真实局部阻断，记录原因后可转向后续输入齐备的独立任务，不使用缺失的前序产物。代码交付与后续环境验证必要时可明确分开，原验收仍保留，不能靠拆任务掩盖未验证。
- 新产物不生成旧依赖列或并行标记。已有 JSON / 工具仍消费旧字段时，不擅自删字段或迁移文件；核对实际消费者，只在已授权范围内调整。旧字段不能代替当前设计与实际输入检查，也不能单凭对端任务未完成阻断本端开发。旧记录与当前交接相冲突时，按原修订权限校正受影响条目；只读检查只指出冲突。
- 每项完成标准同时包含交付内容、本端必要接线、适用异常 / 权限 / 一致性要求和原定最小验证。`done` 须有相应证据；代码已完成但原验证受限时明确注明，状态按业务推进规则保留，不伪装成未写代码或已验收。既有任务拆分 / 合并时先核对代码与历史证据，保留稳定 ID 或替代映射和原完成要求，只调整受影响范围；不自动重写已有实现，也不将旧大项未完成部分标为 done。
- `$pd-fe` / `$pd-be` 开工读取权威任务及本端顺序，缺失 / 漏项 / 顺序矛盾按原 `$pd-plan` 路由校正。每片有结果后更新原任务条目并引用实现 / 验证记录，按共享视图规则刷新项目 TODO（格式兼容例外另沿既有单向派生），再选下一项；汇总直接从权威源按端列已完成与剩余 ID，日志仅保留证据 / 历史记录，不在独立顺序说明或日志中维护第二套当前状态。进度与汇报不要求反复全量重读无变化的长记录；定向读取当前任务、相关变更及阻断依据，既有完成结论受新证据影响时再复核。

### Frontend / Backend 并行开发规则

- 技术设计达到本轮交接条件后，前后端基于同一份已确认契约、技术方案中的两端设计与接线映射，按各自清单顺序并行开发。不等待对端业务代码完成或先通过联调；并行不要求两端始终有人同时执行，也不授权修改对端代码或任务状态。
- 动作码、请求 / 返回字段、权限、状态、错误及分页等必要契约在 `$pd-plan` 交接时确定，不再拆成等待开发确认的契约任务。缺失 / 冲突是设计交接问题：定向核查可信契约 / 源码并回 `$pd-plan` 补证，不从另一端未完成的代码猜契约。
- generated client、SDK、共享 schema / type 等确为当前编码输入时，先判断能否按已确认契约独立生成 / 复用。必要准备排在实际负责端的顺序中，说明产物、真正消费者及验证方式；就绪证据维护在技术方案的真实输入章节或已确认的独立事实源，不另维护任务关系图。产物未生成只影响真正消费者，不阻断输入与工具链已齐备的准备任务；待产出的文件不能又作为其自身必需输入。不强加代码生成或共享包，不把对端整块业务实现包装成“准备工作”。
- 对端真实服务 / 页面可用性通常属于联调或相应验收条件，不自动阻塞基于契约的本端编码。生产地址等仅后续使用的配置待填时，可完成真实调用路径、配置及失败处理，并在本端原定最小验证通过后标 done，保留待联调项；实际构建 / 当前最小验证必需的输入缺失时仍不可标 done。沿用已有相对路径 / 同源路由，不强加绝对 base URL；不虚构地址、类型或成功结果绕过限制。
- 本端原定最小验证仍须执行，不能将必要权限、幂等、事务、资金安全或数据一致性推迟到“等对端”。相关实现完成后按下方联调与验收规则验证真实链路；本端完成不等于完整链路通过。
- 现有顺序若要求等待对端业务进度、先联调再编码，或准备任务自身缺乏可执行顺序，回 `$pd-plan` 校正受影响的清单、设计或输入说明，不能只改任务状态。其他输入齐备且已授权的独立任务继续；不绕过真正契约缺口，也不擅自扩大范围。

### 业务推进、阻断恢复与进度汇报

- 先确定当前授权范围和停止条件。“全部开发完成”“继续完成剩余后端 / 前端”或已明确的连续实现要求，表示在该范围内逐片循环，不是只做一个 slice；后续进度询问不取消原实现授权，简短答复后继续。用户限定单项、只检查、要求暂停或缩小范围时遵从新要求；未有批量授权时不扩成整项目开发。连续授权不包含未获准的提交、推送、发布协议包、SQL 或真实账号 / 订单 / 资金操作。
- `$pd-plan` 按本期确认需求与验收，在 `tech/tech-plan.md` 的实施顺序中组织可验收的业务里程碑：说明入口、关键状态变化、预期业务结果、必要契约 / 依赖及验证信号。沿用已有名称或段落引用，不强加新编号、额外状态文件或固定里程碑数量；局部修复只关联原验收，无需重做全项目规划。金额口径、实际费用来源等决定可行性 / 验收的未知项在设计交接前解决，未解决仍按共享交接规则阻断，不靠先写大量代码掩盖。
- 每个里程碑可拆成多个小的前端、后端及必要准备 slice，任务说明引用同一里程碑 / 验收。前后端基于已确认契约并行实现，各自按本端顺序准备实际必需输入；不把整条大链路合成一个巨型任务，也不将某个里程碑自行解释为获准局部交接未完成的 plan。
- 在追加局部修改或验证前，执行[共享验证规则](#验证与审查)，先确定本次可核验的业务动作、收尾信号和整个纠错循环的限额。输入齐备的同一业务动作可集中实现、共享必要检查，任务状态仍逐项回填；不是每改一个细节就重新构建、统计和汇报。
- 在已有授权、本端顺序和实际输入 gate 内，优先完成当前里程碑仍缺的真实调用接线、状态衔接和持久化，或解除它们所需的工程准备；必要的权限、幂等、事务、资金安全与高风险缺陷随相关链路处理，不能为先跑成功路径而跳过。已有本轮未完成的 slice 先核实能否继续，不反复新开同优先级的零散组件 / 加固任务。已约定并行的独立工作可继续，不因当前里程碑暂受阻而全局停工；无法判定下一项才询问，不机械要求用户在已有明确顺序中重选。
- 未实现 / 未接线如实列为剩余实现；已定义字段的实现漏项、契约本身缺失与需用户决定的业务取舍，按 [共享分类规则](technical-design-rules.md#工程漏项与业务决策分类) 补查和分流，不把内部契约修订自动转成用户审批。环境 / 凭证 / 协议产物不可用写出依赖 ID、受影响动作与证据：先区分编码缺输入、只影响验证、外部操作未获准，不把未写代码称为外部受阻。
- 仅因 SQL 禁止执行、协议包禁止发布或真实环境不可操作而验证受限，但当前设计可交接、编码必需的契约 / 类型 / 工具链等输入齐备时，可继续本 slice 已授权的真实实现和允许的本地检查，不执行被限制的动作。验证依赖仍保留 blocked / unknown 等真实状态，不改成 not-required；原最小验证未通过的 slice 不标 done，也不把未完成的实际产物当作后续输入；后续任务是否可执行按其真实输入与原验证要求判断，不机械等待前项状态。已有 slice 仅因验证受限而 blocked 时，核实上述条件后可补其尚未完成的独立编码，保留 blocked 与原验证缺口；这不等于解除阻断。若原阻断还包含编码输入缺失、决定性契约 / 安全缺口或实际必需产物未就绪，不能借此继续受影响编码。实际编译必需的协议产物缺失也不能用本地替身、虚构类或隔离构建的成功冒充当前目标构建通过。
- 正式解除自己负责的 `blocked` 状态前，读取原阻断记录和当前产物，核实所有原阻断均已解除：实际必需输入 / 工程产物有真实 ready 证据，当前设计与契约仍可交接，且无新增范围或未解决问题。依赖恢复无需重做 plan：回填本 slice 的依赖证据、保留原阻断历史及解除依据，再将其恢复为 `pending` 按正常流程进入 `in_progress`，不能直接标 done。契约 / 范围 / 顺序问题须先有相应上游修订及重新交接的依据，不能仅因某个依赖 ready 就自行解除；原因不明或仍有一项未解除则继续 blocked。上方仅验证受限时的续作始终保留 blocked，不属于解除状态；不修改对端状态，不接管其他执行者的在途任务。
- 每个迭代结束按上方任务清单规则更新自己负责的原任务条目（默认 Markdown；兼容例外沿既有单向派生），回填任务中的简短变更、检查结果与阻断依据，项目 TODO 按共享待办规则刷新；按 [共享业务进度摘要](engineering-contracts.md#业务进度摘要) 汇报实际推进。`done` 不直接推导里程碑真实闭环、联调通过或可上线；验证受限的代码进展如实注明。计数与 ID 从权威源按端读取，不把另一端完成情况混入本端计数。
- **无推进自检**：在追加修改、验证及恢复上下文前，对照原业务收尾信号、剩余限额与上次已核实结果。即使局部修改 / 测试 / 排障证据不断增加，原业务环节仍未接通且限额已到，或连续多轮仍停在同一断点，都须按共享验证规则复核必要收尾条件；不满足条件则退出原循环并纠偏，不等 done 数变化或用户追问。不把同一个固定时长套到所有任务；本次明确的限额仍须执行。没有 done 增长但真实接线 / 状态衔接确有推进时如实记录，不能误判为零进度；排障证据可支持剩余限额内的必要调查，但不能无限抵消业务未收敛或宣称闭环。
- **定向纠偏**：只读当前任务、相关设计 / 代码与最近必要证据，指出当前业务结果还缺哪段，以及未推进是实现未接通、任务过大 / 顺序不当、真实输入缺口，还是缺乏新依据的重复尝试。优先续接已有实现，选出本端一个有明确预期结果和最小验证的下一动作；必要时按原 `$pd-plan` 权限校正受影响任务，保留 ID / 替代映射、原验收和已有证据，不另起全项目设计、批量重写或扩大范围。必要的安全工作、工程准备与有证据的排障不因耗时长被跳过；契约、输入和安全 gate 仍按原规则执行，不为制造进度降低验证或伪标 done。
- **纠偏后续作**：将比较结果、原因、调整、未完成环节、剩余限额 / 耗尽后的恢复条件及下一任务 ID / 动作简短回填原任务的结果 / 证据 / 阻断或当前续作，并复用业务进度摘要说明，不新增停滞报告、计时台账或状态来源。连续授权下直接执行该动作；下次更新核对其实际结果，仍无增量时改用有依据的其他路径或按原规则处理阻断，不重复空转、自检或反复重排同一任务。局部受阻转向其他输入齐备的获准任务；确实没有获准可执行动作时按下方停止条件交接，不忙等、不越权操作，也不把纠偏本身当作交付完成。
- 连续执行时，单片完成、遇到局部阻断或写完进度摘要后，都核对权威源中当前条目和下一可执行候选，继续具备条件的编码或允许的验证；总表无相关变化时不反复全量重读和统计；摘要作为过程中更新，不以“下一步可以继续”替代执行。仅验证受限且已无剩余可写代码 / 可做检查的 slice 不重复选取；记录后转其他独立任务，不忙等同一环境，也不接管他人任务。任务缺失、范围覆盖不全或顺序不可执行先按原 `$pd-plan` 路由处理，不能把空列表当成全部完成。
- 结束前核对原授权范围：仅在范围已完成、用户要求停止 / 达到其限定范围，或逐项核对剩余任务后确实没有获准可执行动作时结束。最后一种情况须列剩余任务 ID、已完成代码与未写部分、阻止下一步的具体依据、需要谁做什么及恢复入口；只阻断相关任务，不以笼统“受阻”结束仍有可写代码的整轮工作。若执行被中断而未完成，保存当前任务和下一项据实交接，不把中断写成完成或环境阻断。
- 不默认报告整体完成百分比，也不凭文件数、代码行或测试数估算。用户明确要求数字时，只报告有依据的统计并写明范围、分子 / 分母、计算口径和未覆盖部分；已验收任务数占比仅是任务验收计数，大小不等的切片不直接折算业务完成百分比。没有可靠依据时明确无法估算，同时给出上述业务进度摘要。

### 联调与验收交接

- 在任务清单中明确联调 / 测试要验证的业务结果、关联实现 ID、真实输入与通过条件，引用原验收，不复制一套开发状态。正式联调前从权威源核对范围内相关前后端实现及必要准备均已完成，并核实实际输入就绪；不等待无关任务，不靠遗漏相关实现或临时缩小范围绕过验收。完整交付仍保留所有原验收与必要安全 / 资金验证。
- 联调 / 测试是相关实现完成后的验收衔接，不是开发的前置任务。开发期间输入齐备的测试和只读检查仍可先执行，其结果不替代正式联调或总体通过结论。
- 契约完成依据在 `tech/tech-plan.md` 的交接结论及关联设计维护，不强制创建独立契约任务或“契约确认 + 实现”两段任务。工程初始化、依赖准备、迁移文件及真实 client 等实现动作归实际负责端；不能用契约确认记录替代实现与验证。
- 联调 / 测试或 UI 审查发现契约明确的实现偏差时，核对 `implementation-defect` 分类、原契约 / 设计、实现证据及已有本端任务，可重开该任务并保留历史，不先造新的待办或等整轮联调通过再修。UI finding 按 [修复交接](ui-review-rules.md#6-ui-finding-修复交接) 处理。
- 确认权威任务源无覆盖、需改共享契约 / 数据模型 / 权限 / 页面路由或范围时回 `$pd-plan`；先排除派生视图滞后，不单方面扩任务。原定验证失败或真实输入缺失仍记录具体缺口，不能靠删除依赖列放行。

## 9. Review 严重级别

`$pd-review` 输出的问题必须使用：

```text
P0: 阻断发布
P1: 必须修复
P2: 建议修复
P3: 可选优化
```

UI 采用同一套 P0/P1/P2/P3，用户影响、证据不足及残余风险的判断统一见 [UI Review Rules](ui-review-rules.md)，不在各阶段重复维护定义。

## 10. Git 与发布边界

- `$pd-git` 默认只准备 commit / PR 文案。
- 用户明确要求时，`$pd-git` 可执行 `git add` 和 `git commit`。
- 执行 `git add` 前必须展示 planned files、excluded files、possible missing files、possible extra files 和 staged 差异，并排除明显无关文件。
- 提交前必须检查 `.gitignore` / ignored / untracked 状态；构建产物、缓存、日志、截图、临时报告和历史 benchmark run 默认不提交。
- 不使用 `git add -A`、`git add .` 或通配符扩大提交范围；只逐个 add 已确认的 planned files。
- staged 文件与 planned files 不一致时，不继续提交，先说明差异并等待确认。
- 有未解决 P0/P1、失败测试或未解释的契约差异时，不建议提交。
- 默认不 push，除非用户明确要求。
- `$pd-release` 只生成通用 Markdown 上线文档，不接平台、不部署。
