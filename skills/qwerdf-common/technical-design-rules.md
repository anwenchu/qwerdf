# 技术设计依据与范围规则

用于 `$pd-plan` 的设计交接，以及 `$pd-fe`、`$pd-be`、`$pd-review` 对方案的核对。模板只记录结论与引用，不在各入口重复维护规则。

## 1. 先限定本轮问题和交付范围

- 从用户当前要求、已确认 PRD / 验收和已有决定提取业务目标、本期链路、涉及对象、改动边界和非目标。已有稳定需求编号沿用，没有编号可引用原文位置，不为填表强制重编号。
- 每项拟修改的模块、依赖、接口、表或任务，都应能关联已确认需求，或解释它为何是完成该需求不可缺少的技术前置。发现现状缺陷不等于获准修复它；“顺手兼容全系统”“统一所有旧接口”不能代替本期必要性说明。
- 区分**改动范围**和**只读影响核查范围**。可沿本轮调用链、共享读写约束、直接调用方和实际依赖做有理由的核查，写明要回答的问题及何时停止；不因共享一张表、同一字段或同一个组织概念，就把所有相关业务加入本期。
- 发现范围外问题时记录位置、影响依据及是否已证实关联本期；一般建议单列，不进入本期方案承诺、SQL 或 task slices。确实会破坏本期链路或验收时，说明最小必要变更和不做的后果；已有授权沿用，尚未授权的范围变化先确认，不扩大到无关业务改造。

### 现有能力与新增设计必要性

- 展开新增表、字段（含生成列）、约束、状态、开关或公共抽象前，先沿本期链路核对已有能力：字段真实语义、数据粒度与生命周期、键的作用域、实际读写方及既有行为。能满足已确认场景时优先复用；确需新增时，说明哪个已确认场景或有依据的工程约束无法由现有方案满足，以及最小增量和影响。“更安全”“以后扩展”或行业惯例本身不是依据；复用也不能靠篡改既有字段语义或破坏兼容性成立。
- 新增 / 改变业务资格、拒绝条件、状态门槛、外部查询前置或重试 / 补偿规则，即使未加表 / 字段 / 类，也须关联已确认场景或有证据的工程不变量，说明合法请求受到什么影响、原能力为何不足。普通空值防护不逐个报批；仅凭“更安全”不得发明业务阻断。删除既有检查前先追到它保障的归属、资金、并发、幂等、事务或未知结果约束及承接位置，缺少文档不等于可删。
- 出现唯一约束冲突、状态 / 补偿层层增加或为旧方案不断加保护时，先回查最初的业务粒度、字段映射和前提是否成立，再决定修正用法还是增加结构。确有并发、权限、事务、历史追溯或未知结果风险时保留所需机制；减少结构前须说明原不变量由什么承接，不能单凭字段 / 类更少就删锁、唯一约束、审计或恢复能力。
- 必要性依据写在 `tech/tech-plan.md` 原决策 / 设计段落，关联已有契约和源码定位，同一决策的相关改动可合并说明；不为每个局部方法另写论证、不重复证明未变决定，也不新增论证文档或全库排查。实现时将实际结构及行为增量与这些决定对照；新增或替换设计需要修订时，沿既有工程漏项分类与设计交接规则原位同步，不能先偷偷扩展再用补文档掩盖偏差。已有授权内的工程修订不新增用户审批，真正改变业务规则或范围才确认。
- 审查分别判断行为是否正确、设计增量是否必要以及实现是否符合方案；测试通过或方案已有此设计，均不单独证明新增合理。在原审查报告引用具体增量、依据及取舍；只读审查不直接删结构或改方案。必要性拿不准时列出待复核事实，不靠关键词、数量或个人风格自动判错；已证实的问题按实际行为风险或维护影响分级，不一律阻断或升级为 P1。简化后的必要安全验证、回归及原验收仍须满足，不借本规则反复重开未变设计或重跑有效检查。

### 仓库、分支与二方包版本

- 技术设计开始时，必须先确认本轮需要修改的仓库及各仓库的开发分支名，覆盖前端、后端和确需修改的二方包提供仓库；只读参考仓库与修改清单分开。优先沿用用户当前要求、会话或已有设计中明确确认的约定，不重复询问；当前检出分支或远端默认分支本身不代表用户已确认。缺少明确约定时先定向确认，可继续必要的只读定位，但不先产出正式技术方案或交给开发。
- 在 `tech/tech-plan.md` 维护唯一的仓库 / 分支 / 二方包版本记录，写清路径、改动归属、已确认分支和确认依据，任务及各端设计引用它。新增修改仓库或变更分支须先完成相应确认并同步受影响设计，不把扫描到的仓库自动纳入实施。
- 本轮修改的二方包，其开发版本一律为 `<该包提供仓库已确认的开发分支名>-SNAPSHOT`，按分支名原值拼接。前后端涉及二方包改动时遵守同一规则；消费者引用提供方的该版本，不按消费者自己的分支另造版本。未修改的包和第三方依赖沿用已核实版本，不为格式一致强制改号。若实际工具链不接受该版本值，先说明具体限制并确认兼容的分支名，不擅自删分支前缀、替换字符或更换版本格式。
- 版本在项目既有权威定义处维护，核对父项目 / BOM / 集中版本变量、实际提供模块及相关消费者的生效版本，不复制多套版本记录。版本确定不等于制品已构建、已发布或消费者已解析到它；真实产物准备仍按依赖门禁，发布权限须另有授权。
- 前后端每次开始或恢复实现前，都须对照该记录只读核对目标仓库、实际检出分支及本轮相关二方包的版本 / 依赖引用；不一致时先处理受影响范围，不在未知或错误分支上编码。已授权开发时可按已确认分支复用或准备工作区，先核对未提交改动，不覆盖或丢弃无关工作，不重复索要已有授权。只读任务不切换或创建分支；该记录不授权提交、推送或发布制品。只读审查缺少记录时如实指出交接缺口，不因此停止其他可完成的只读检查。

## 2. 关键技术结论要能追溯

- 区分源码 / 契约事实、设计提案和未确认项。定位使用仓库 / 模块、路径、符号与必要行号；依赖版本、分支或配置差异会改变结论时记录对应版本和适用条件。没有取得的证据明确写缺失，不能编造文件、类、接口或行号。
- 复用关键接口时，说明调用方、提供服务及协议全名：例如 HTTP method + path、gRPC service/method 或消息 topic / 事件类型；追到可信契约和已有调用 / 绑定证据，能取得时核对提供方实现。本次首次接入时可明确拟新增调用位置，不强求已有调用代码。外部闭源服务可引用相应版本的官方契约、可用 client / 配置和验证证据，不强求不可取得的源码。
- 写清业务身份 / 账户 / 租户等关键参数从哪里取得、如何映射到请求，消费返回的哪个字段、其口径 / 单位 / 状态语义，以及权限、前置校验、执行顺序、异常 / 空值与恢复路径。按本轮风险覆盖幂等、并发、事务和副作用，不用“调用资产服务”“查询用户”“复用原接口”代替接入设计。
- 源码声明、依赖可见性、实际装载和运行可用性是不同证据。涉及同名类、多个依赖包、路由 / 开关或环境配置时，核对本模块实际依赖版本、装配 / 调用配置及可取得的验证；只查一个包不能断言必须升级依赖或修改公共库。决定性装载证据缺失时保留条件结论，不拿猜测补全。
- 新增接口、类、表或字段可作为明确的**拟新增设计**，说明归属、契约、实现任务和验证方式；不因尚未实现就否定设计，也不得把拟新增能力说成现有可用能力。证据定位集中在相关设计段落或索引，其余产物引用，不复制多份易漂移的事实表。

### 工程漏项与业务决策分类

- 发现缺字段、参数未传或下游接入不完整，先在本期链路内核对已确认需求 / 决定、现有设计与版本契约、调用方和可取得的提供方实现，定位缺在采集、校验、DTO / client 传递、下游实际消费还是返回处理。证据可取得时先查，不将尚未核查的工程问题直接升级成“需要用户决定”；找不到依据时明确缺什么，不能靠行业习惯猜规则或无限扩查。
- 在已获准的功能与改动范围内，已有契约明确、实现位置和语义有据可循的工程漏项，直接按本端已有 slice 补齐并验证；已交付实现错误走既有 implementation-defect 路线，不重复询问是否要满足已确认要求。若需要补 API 契约、页面规格、数据模型或任务覆盖，先回相应设计入口完成最小修订、同步受影响产物并重新核对交接，不能由实现者单方面改契约。此类内部修订不自动成为新的用户审批；没有实际业务选择或范围变化时，沿用已有授权继续，仍遵守只读要求、阶段及外部操作权限。
- 真正需要用户决定的是现有事实无法决定、且会改变业务结果 / 规则或授权范围的取舍，例如变更账号唯一性、合并历史身份、决定历史数据归属或改变资金口径。只问尚未确定的那部分，说明已查证据、具体分歧、最小选项与推荐；既有决定不重问。补查后仍缺且只能由用户提供的关键输入，也应定向提问并保留未知，不伪装成已确认的工程漏项。
- 例如已确认手机号注册且可信契约要求拨号区号，缺采集 / 漏校验 / 漏传区号属于本期接入漏项，不再问“要不要采集区号”。字段值由终端用户通过注册输入提供，或按已确认规则来自已有可信资料；格式及转换按契约核对，不能按字段名把国家标识、国籍或界面语言等同拨号区号，也不猜一个默认区号；已有完整号码输入方案可沿用，不强制新增重复选择控件。
- 字段采集、透传和查询实际生效分别核对：下游若仍忽略已确认身份边界中的区号或租户 / 来源，只补 UI 或请求字段不算修复。按当前任务归属补齐实现，确需契约修订则回设计，不扩大成全系统账号治理。查询返回一条也不自动证明身份归属 / 授权，既有持有验证、可信作用域和完整匹配要求不能省略。零结果按已确认的新注册分支处理，不能当成已找到旧用户；多结果、字段不匹配或证据不足时，暂停受影响的绑定 / 资金初始化，不擅自取第一条或重绑，不把未经核实的候选当注册成功。取得合法创建 / 复用结果且安全条件满足后按原流程继续，阻断与继续范围仍遵守既有交接和依赖 gate。

## 3. 交付应足以让实现者执行

- 先识别本轮是设计、设计检查、设计修订还是已授权的实现。用户只要求“检查 / review 设计”时只读核查并报告，不修改业务代码或把任务推进到开发；审查完成不等于设计通过。用户已要求“设计完成后继续开发”时沿用授权，但必须先满足下述交接条件，不能把这句话当作设计已完成的证据。
- 对本轮关键链路写清入口到依赖再到结果的步骤，以及复用位置、拟修改 / 新增位置、关键数据映射、失败处理和验证信号。实现者不应再猜“调用哪个服务哪个方法”“账户 ID 从哪里来”“返回字段如何用于业务判断”。简单局部修改说明受影响步骤即可，不要求为每个辅助方法补完整调用链。
- 决定可行性、权限、金额语义、共享契约或验收的未知项未解决时，只能报告草案 / 受影响部分待补 / 阻断，不能仅凭文件齐全称设计完成，也不能以任务已完成掩盖契约缺口。说明缺口、影响范围、所需证据和下一步；可以继续独立部分的设计核查，不把局部未知无限扩大成全项目停工；正式实现交接仍须满足既有契约和依赖 gate。
- 清楚定义且无决定性未决项的新设计可以交接，待实现的代码本身不是设计缺口。已确认的源码设计也不等于已部署 / 已联调；环境就绪状态在技术方案的真实输入章节或已确认独立事实源按适用任务维护，真实环境验证留给对应阶段，不能伪报通过。
- 交接前用读者视角沿本期验收走查：技术接入是否具体、有依据，任务是否都服务本期，未决项是否暴露，开发者能否据此实现并验证。自由文本的真实性、因果关系和范围必要性由审阅判断，不用标题齐全、关键词命中或未经执行的脚本输出替代。
- 完成判断覆盖本轮约定的设计范围：对照已确认验收，串查 API、数据模型与唯一约束、权限 / 状态 / 错误、必要并发 / 事务、接入依赖及任务验证是否一致；只核对本轮适用项，允许引用未变的既有设计。发现矛盾或决定性缺口须写出依据、影响和待解决项，不能移进风险章节后仍宣称全方案完成。仅在用户已明确分期交付时，可按已划定且无共享未决契约的独立范围交接；不得临时缩小范围来绕过未完成的 plan。
- 在 `tech/tech-plan.md` 的交接结论记录本次核查范围、依据、未决项及可交接判断，任务表引用对应设计。进入实现前读取当前设计和已有缺口 / 审查记录核对，不仅相信旧摘要、文件存在或历史契约任务状态。不要求另建审批文件、全量重做历史方案或重复确认已定业务规则。
- 设计是否明确、开发依赖是否就绪、实现 / 运行是否验证须分开报告：未发布协议包可能阻塞消费者，但不自动否定已明确的协议设计；尚未执行 SQL 不证明表约束设计有误，也不自动阻塞只编写迁移文件。按该操作是否为目标 slice 实现或最小验证的必要条件，在既有依赖清单记录实际状态；不得借此绕过必需依赖 gate，或把未验证写成已验证。

## 4. 实现与审查的回退

- 新证据暴露已交接设计的冲突 / 决定性缺口时，旧的“可交接”结论对受影响范围失效。只读检查须明确指出哪些旧结论和任务状态已不可信；获准修订时，在同轮同步对应设计、交接结论及受影响任务的状态 / 阻断说明，不能只加一份缺口报告而保留相反结论。保留已有实现及验证历史，不删除代码、不把已完成工作冒充从未执行，也不自动扩成全项目返工。
- 实现阶段先按 [工程漏项与业务决策分类](#工程漏项与业务决策分类) 补查与分流；若关键现有能力、参数来源或字段语义仍需猜测，按契约 / 设计缺口回 `$pd-plan` 补证，不由实现者静默发明接入或扩大任务。契约清楚但实现不符时仍沿用既有 `implementation-defect` 修复路线。
- 审查核对“引用是否支持结论”“改动为何属于本期”，并按 [新增设计必要性](#现有能力与新增设计必要性) 判断结构及行为增量是否合理，不能只看代码能否运行。证据不足标未确认，已证实偏离范围或关键设计不可执行时按真实影响分级；相关建议不能自动升级为新增需求、依赖升级、迁移或全系统整治任务。
