# 需求质量与交接检查

本文件用于需求定义及自审，不生成技术实现。用户指定的格式和交互节奏优先；下列检查只用于本次范围。

## 输入与事实

1. 先读现有材料及用户已确认的决定，再补问会改变业务规则、范围或验收的缺口。不重复询问已有答案，不固定要求多轮问答。
2. 记录事实、来源及确认状态，新材料建议使用 SRC 编号，已有稳定编号沿用。区分已确认、假设和待确认；记录原文位置、文件段落或会话决定。竞品事实可以描述竞品，不能据此确认本产品需求。
3. 目标说明要改善谁的什么问题及如何判断改善。已有基线、指标口径、目标值和约束按来源填写；没有数据时明确待验证，不能为了完整而编数值。
4. 范围、非目标、优先级及关键取舍应可解释。角色、资源归属、可见范围、触发条件及成功结果应足以让设计和研发理解；避免用接口字段或数据库结构代替业务规则。

## 需求到验收

- 需求和验收使用稳定编号，新建建议 REQ / AC，旧编号不强制转换。正式需求引用已确认来源；验收表维护 AC → 需求关系，允许一条 AC 关联多个需求。需求清单、用户故事和覆盖表无需另列全 AC；旧摘要如保留编号，应与权威关联一致。
- 验收写清前置条件、操作或事件、可观察结果。例如“无权用户看不到其他租户记录，直接访问也不能获取记录”，比“权限正确”更可验证。
- 审阅适用的正常结果、异常与恢复、权限与可见性、边界与重复操作、状态流转。复杂或高风险需求可加覆盖矩阵，只记录需要解释的关联或不适用原因；无需每个需求填五维表，不扩展来源中不存在的规则。省略矩阵不等于省略业务审阅。
- 有状态的对象写清允许 / 禁止的流转及失败后的状态；有重复提交、超时、取消、部分成功或并发修改风险时，先明确用户可见结果，不替研发选择锁、事务或重试实现。
- 有 UI 的需求覆盖适用的加载、空态、错误、权限与保存反馈；没有 UI 不强制生成页面状态。UI 状态不能代替订单、审批等业务生命周期。
- 开放问题标明影响、是否阻断、状态和确认方。涉及权限、金额口径、状态转换或核心验收的未知项通常阻断受影响需求交接；不通过默认值或“不适用”绕过。非阻断问题的确认方可待定，保留提醒即可。

## 校验和读者自审

可运行时先用共享工具的 `validate --stage prd`，脚本不改文件。`BLOCKED` 表示检测到重复编号、明确错误引用、矛盾关联、正式需求使用未确认来源、已识别需求无验收或未解决阻断问题；修正或澄清后重跑。`REVIEW` 表示缺表、缺字段、格式无法识别或内容需要语义判断；保留原格式人工核对，只有实际业务缺口阻断受影响范围。`PASS` 表示未检出机械问题，不能证明业务正确。退出码 0 包含 `PASS` 和 `REVIEW`，自动化必须检查 JSON 的 `status` 或 `passed`。

开放问题只识别到部分表格时，表外正文或其他格式仍需人工核对，包括可能只是背景的说明；工具不靠词语判断其是否阻断。已识别的明确阻断项仍生效，不因另有未知格式而放行；无需把原有说明改成表格来消除 REVIEW。

再仅依靠产物回答这些问题，检查读者是否必须猜测：

- 谁在什么条件下可以操作什么对象，能看到什么？
- 成功、失败、拒绝、边界和重复操作后分别发生什么？
- 哪些属于本期，哪些明确不做，依据在哪里？
- 每项需求怎样验收，什么问题还会阻断设计？

记录具体矛盾或缺口，不因文件齐全、标题齐全或脚本通过而声称需求已确认。机械检查通过或等价人工核对完成，且业务自审无未解决阻断项时，才建议 `$pd-blueprint`。Python 不可用、用户格式或旧材料不适配时，人工核对来源、稳定关联、业务覆盖和开放问题，记录结论及未核实项即可，不重排用户格式、不伪报脚本通过。`REVIEW` 尚未核对前不能当作已完成交接。

## 旧材料与局部修订

- 可读取旧版平铺文件；新写入仍用 canonical path。旧材料按现有表达核对，不为消除格式提示补齐全部历史编号或覆盖表，也不能声称已通过未执行的检查。
- 局部修改只更新受影响的规则、来源、需求、用户故事、AC 和问题；不自动重写其他章节或扩大产品范围。
